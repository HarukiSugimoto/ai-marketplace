# build-report — 1枚の HTML にまとめる

build-kit の最終段階。ここまでの成果を**ブラウザで見返せる形**にする。
チャットを遡らなくても「何を作って、何が証拠で、何が残っているか」が分かる状態にするのが目的。

## 5原則(build-kit 共通)

1. **スコープ宣言** — 触る範囲を先に宣言する。宣言外に手が伸びたら**止まって報告**。黙って広げない
2. **証拠なき完了宣言の禁止** — 「できた」と言うには証拠が要る。「通るはず」は証拠ではない
3. **段階ゲート** — **判断がユーザーのものである境界**では必ず止まる
   (設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。
   逆に「作業を続けていいですか」だけのためには止まらない — それは判断ではない
4. **気づきの報告義務** — 気づいたことは**必ず言う。ただし実行はしない**。
   言うことが無ければ「無し」と書く。**黙って見送るのは違反**
5. **出力の型** — 1行目は結論か次の行動。**段階の現在地(どの段階か / T2 of T5 のどこか)を毎回書く**。
   前置きと締めの挨拶を書かない。詳細は `${CLAUDE_PLUGIN_ROOT}/templates/output-style.md`

レポートは 2 の最終防衛線。**⚠️ を ✅ に書き換えて綺麗なレポートを作らない。**
未確認が残っているレポートは、未確認が残っていると表示されるのが正しい。

## Step 0: 入力を集める

| 情報 | どこから |
|---|---|
| 題名 / slug / 日付 | `<docs_dir>/<日付>-<slug>/` のディレクトリ名と design.md |
| 受入条件と証拠 | build-verify の判定表 |
| 検証コマンドの出力 | build-verify で実際に走らせた結果(exit code 込み) |
| 変更ファイルと理由 | `changes.md`(build-run が書いたもの)。無ければ `git diff --name-status` + 各ファイルの理由を補う |
| スコープ照合 | plan.md のスコープ宣言 vs 実際の `git status` |
| タスクの消化状況 | plan.md のチェックボックス |
| 気づき / 積み残し | 各段階の「気づき」欄を集約 |

build-verify を通っていない場合、**レポートを作る前に build-verify に戻す。**
検証していないものをレポートにしない。

## Step 1: report.json を書く

`<docs_dir>/<日付>-<slug>/report.json` に書く。
書き方は `${CLAUDE_PLUGIN_ROOT}/templates/report.example.json` を見る。

主要フィールド:

- `verdict` — `完成` / `条件付き` / `未完` のいずれか。build-verify の判定をそのまま入れる
- `acceptance[]` — `status` は `pass` / `warn` / `fail`。**`warn` を `pass` に丸めない**
- `changes[]` — `why` に**なぜ変えたかを1行**。ここが空のレポートは価値が半減する。
  宣言外のファイルは `inScope: false` にする(レポート上で赤く出る)
- `checks[]` — 実際に走らせたコマンドと exit code と出力。**捏造しない**
- `notes[]` / `leftovers[]` — 空配列なら「無し」と表示される。無理に埋めない
- `diff` — **`git diff` の生出力をそのまま文字列で入れる**(下記)

### diff の取り方

```bash
git diff <BASE>...<HEAD>
```

`<BASE>` は作業開始時のコミット(build-verify の Step 3 で使ったものと同じ)。
まだコミットしていないなら `git diff` だけでよい。

**加工しない。** unified 形式のまま渡す。`report.mjs` がハンクヘッダ
`@@ -12,9 +12,20 @@` を読んで**旧側・新側の行番号を復元し、GitHub と同じ形で描画する。**
`--stat` や `--name-only` に置き換えない(行番号が出せなくなる)。

差分が巨大なとき(数千行)は、レポートが重くなるのでパスを絞る:

```bash
git diff <BASE>...<HEAD> -- <plan.md のスコープ宣言にあるファイル>
```

**絞ったことをレポートの `summary` に書く。** 黙って一部だけ載せない(原則4)。

## Step 2: HTML を生成する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/report.mjs" <docs_dir>/<日付>-<slug>/report.json
```

同じディレクトリに `report.html` が出る(`-o` で出力先を変えられる)。
依存ゼロの自己完結 HTML、白基調、**タブ3枚**:

| タブ | 中身 | 元データ |
|---|---|---|
| **計画** | 受入条件(条件のみ)・タスク消化・スコープ宣言 | `plan.md` |
| **変更内容** | 変更ファイルと理由の表 + **行番号つき差分** | `changes.md` + `git diff` |
| **総評** | 判定・受入条件×証拠・検証コマンドの出力・スコープ照合・気づき・積み残し | build-verify |

受入条件は**計画タブに条件だけ、総評タブに証拠つきの判定**が出る。役割が違うので重複ではない。

## Step 3: 開く

```bash
open <docs_dir>/<日付>-<slug>/report.html      # macOS
```

## Step 4: gitignore を確認する

`report.html` は**生成物なのでコミットしない。** 対象 PJ の `.gitignore` に
`*.html` が無い場合、次の行の追加を提案する(勝手に追記しない — 原則4):

```gitignore
# build-kit の生成物
docs/dev/**/report.html
```

`report.json` は入力なので、残すかどうかはユーザーに聞く。
`design.md` / `plan.md` / `changes.md` は成果物なのでコミット対象でよい。

## Step 5: 締め

> レポート: `<パス>`
> 判定は <完成 / 条件付き / 未完>、受入条件 N 件中 達成N / 未確認N / 未達N。
> 積み残し: <列挙、無ければ「無し」>
> 気づき: <列挙、無ければ「無し」>

**積み残しがあるなら、それを次の build-design に送るかどうかをユーザーに聞く。**
勝手に次のサイクルを始めない。
