# build-verify — 証拠を出す

build-kit の第4段階。**「できました」と言ってよいかを判定する。** 次段は build-report(HTML レポート)。

## 5原則(build-kit 共通)

1. **スコープ宣言** — 触る範囲を先に宣言する。宣言外に手が伸びたら**止まって報告**。黙って広げない
2. **証拠なき完了宣言の禁止** — 「できた」と言うには証拠が要る。「通るはず」は証拠ではない
3. **段階ゲート** — **判断がユーザーのものである境界**では必ず止まる
   (設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。
   逆に「作業を続けていいですか」だけのためには止まらない — それは判断ではない
4. **気づきの報告義務** — 気づいたことは**必ず言う。ただし実行はしない**。
   言うことが無ければ「無し」と書く。**黙って見送るのは違反**
5. **出力の型** — 1行目は結論か次の行動。**段階の現在地(どの段階か / `02 of 05` のどこか)を毎回書く**。
   前置きと締めの挨拶を書かない。詳細は `${CLAUDE_PLUGIN_ROOT}/templates/output-style.md`

この段階は 2 が全て。

## 鉄則

```
このメッセージの中で実際にコマンドを走らせていないなら、通ったとは言えない
```

以下は**証拠ではない**:

- 「前に走らせたときは通った」
- 「変更内容から見て通るはず」
- 「型エラーは出ていないので大丈夫」
- 「ロジック上は正しい」
- テストの**一部**だけ走らせた結果

## Step 0: 入力を読む

1. `.build-kit/config.yaml` — 検証コマンド(`test` / `typecheck` / `lint` / `build`)、
   `known_failures`、レビュー設定(`review_skill` / `review_command` / `standards_files` / `review_focus`)
2. `plan.md` の「受入条件 → テスト対応」表
3. `changes.md`(あれば)

config が無ければ、`/build-setup` を勧める。無いまま進めるなら、
検証コマンドをここでユーザーに聞く(**推測で走らせない**)。

## Step 1: 前提条件を通す

型チェックとビルドは**通って当たり前**の前提条件であって、機能ができた証拠ではない。
まずここを緑にする。

| 対象 | コマンド | 記録するもの |
|---|---|---|
| 型チェック | `typecheck_command` | exit code と出力の要点 |
| lint | `lint_command`(空なら省略) | exit code と指摘件数 |
| ビルド | `build_command`(空なら省略) | exit code |

赤ければ**ここで止まる。** 直してから先へ進む。

**lint が見るものは、後段の Standards レビュアーに二重に見せない。**
機械が弾くものを人間の目で再確認する意味はない。

## Step 2: テストを全部走らせる

`test_command` を**丸ごと**走らせる。今回のテストだけではなく全体を走らせる
(既存テストを壊していないことの確認も兼ねる)。

記録するもの: **実行したコマンド / exit code / 何件通って何件落ちたか。**
「全部通りました」ではなく「42 passed, 0 failed」と数字で書く。

落ちているものがあれば、それが**今回の変更由来か既存の失敗か**を判別して報告する。
config の `known_failures`(セットアップ時点で既に赤かった件数)が判別の基準になる。
既存の失敗を今回の成果に紛れ込ませない。

## Step 3: 2軸レビューを並列で投げる(★この段階の核)

ここまでで**コマンドの出力という材料**は揃った。判定はここから。

**判定を自分でしない。** 実装した本人は「動くと知っている」ので、証拠が無い項目を
無意識に ✅ に丸める。会話履歴を持たない目に判定させると、書かれた証拠だけで
判断せざるを得なくなる。

そして軸は2つある。**片方が片方を隠す**ので、混ぜない:

> 規約を全部守っているが間違ったものを作った → Standards 合格 / Spec 不合格
> 仕様どおりだが規約を壊している → Spec 合格 / Standards 不合格

### 2体を1メッセージで同時に投げる

汎用サブエージェントを**2体、同じメッセージの中で並列に**起動する
(順番に投げない。互いの結論を汚染させないため)。

使うエージェントはハーネスで名前が違う:

| ハーネス | 汎用エージェント |
|---|---|
| Claude Code | `general-purpose` |
| Codex | `default`(汎用) / 並列に多数投げるなら `worker` |

**並列に2体投げられない環境では、Spec 軸を先に投げ、その結果を渡さずに
Standards 軸を投げる。** 順番になるのは仕方ないが、**片方の結論をもう片方に見せない**
という条件だけは守る(見せると軸を分けた意味が消える)。

| サブエージェント | 雛形 | 見るもの |
|---|---|---|
| **Spec 軸** | `${CLAUDE_PLUGIN_ROOT}/templates/reviewer-spec.md` | 受入条件を満たしたか。✅/⚠️/❌ の3値判定 |
| **Standards 軸** | 下記(PJ 設定で分岐) | 規約準拠とコード品質 |

#### Standards 軸は PJ 固有のものを優先する

**このPJに専用のレビュー手段があるなら、build-kit の汎用レビュアーより正確。**
config を見て分岐する:

| config | Standards 軸で何をするか |
|---|---|
| `review_skill` が設定済み | **その skill / スラッシュコマンドを使う**(例: `/check-spec` で設計書との整合性を見る) |
| `review_command` が設定済み | そのコマンドを実行し、出力を Standards 軸の結果に含める |
| どちらも空 | `${CLAUDE_PLUGIN_ROOT}/templates/reviewer-standards.md` の汎用レビュアーを使う |

両方設定されているなら両方回す。**PJ 固有のものを汎用で置き換えない。**

両方に埋めるもの:

- `[BASE]` — 作業開始時のコミット(`git merge-base` か plan.md 作成時の SHA)
- `[HEAD]` — 現在の HEAD
- Spec 側: `[PLAN_PATH]`(plan.md のパス)と `[TEST_OUTPUT]`(Step 2 の実行結果)
- Standards 側(汎用レビュアーを使う場合): `[STANDARDS_FILES]` は config の `standards_files`
  (無ければ `CLAUDE.md` / `CODING_STANDARDS.md` / `CONTRIBUTING.md` を探す)。
  config に `review_focus` があれば、その観点を雛形の末尾に足して渡す

**セッションの会話履歴は渡さない。** 差分・計画・コマンド出力・規約だけ渡す。
「こう実装したので大丈夫なはず」という作った側の言い分を混ぜない。

### 結果を並べる(マージしない)

```
## Spec 軸(受入条件)
## Standards 軸(規約・品質)
```

**ランク付けし直さない。** 分けている意味が消える。
最後に1行、**それぞれの軸の最悪の指摘**だけ挙げる。軸をまたいで優劣を決めない。

Spec 軸に ⚠️ / ❌ があるか、Standards 軸に Critical があるなら、
Step 5 の判定は「完成」にしない。

### サブエージェントの結果を書き換えない

返ってきた ⚠️ を、自分の知識で ✅ に直さない。
「実際は動いている」と思うなら、**その証拠を取ってから**もう一度判定させる。
判定表を手で書き換えるのは原則2の違反。

## Step 4: スコープを照合する

`git status` / `git diff --stat` を実行し、**実際に変わったファイル**を
`plan.md` のスコープ宣言と突き合わせる。

| 照合結果 | やること |
|---|---|
| 宣言どおり | そう報告する |
| **宣言に無いファイルが変わっている** | 一覧にして報告し、意図的か確認する |
| 宣言したのに変わっていない | 実装漏れの可能性。タスクの取りこぼしを確認する |

ここで初めて気づいた宣言外の変更は、**原則1の違反として明示的に報告する。**
「結果的に必要だった」で流さない。

## Step 5: 判定を出す

以下のどれかを、はっきり述べる:

- **完成** — 受入条件が全て ✅、テスト全緑、スコープ宣言どおり
- **条件付き** — ✅ だが ⚠️ が残る。**何が未確認かを列挙する**
- **未完** — ❌ がある。何が足りないかを列挙する

**⚠️ が1つでもあれば「完成しました」と言わない。**「条件付き」と言う。

## Step 6: 次の行き先

判定によって分かれる。

### 全て ✅ のとき — 止まらずレポートへ

> 検証結果: 完成。受入条件 N 件すべて達成、テスト N passed / 0 failed、スコープ宣言どおり。
> 気づき: <列挙、無ければ「無し」>
> 続けてレポートを出します。

**承認を待たずに build-report に入る。** レポート生成に判断は要らない。

### ⚠️ か ❌ があるとき — ここで止まる

> 検証結果: <条件付き / 未完>。受入条件 N 件中 ✅N / ⚠️N / ❌N。
> 未確認: <列挙>
> 未達: <列挙>
> Standards 軸の Critical: <列挙、無ければ「無し」>
>
> どうしますか。
> 1. 先に潰す(build-run に戻る)
> 2. このままレポートに残す(未確認は未確認として記録される)

**勝手に「まあいいか」で先に進まない。** ここは判断が要るので止まる。
ただし選択肢を出して待つだけにして、**未確認を黙って ✅ に変えない。**
