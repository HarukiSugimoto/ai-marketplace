# build-run — 計画どおりに実装する

`plan.md` のタスクを**1つずつ**片付ける。
**通常は build-plan の承認ゲートから自動で入ってくる**(単独でも呼べる)。

**この skill は実装だけで終わらない。** 全タスクが終わったら、確認を待たずに
build-verify → build-report まで通し、**レポートを開いて終わる。**

```
RED→目視→GREEN→REFACTOR を1タスクずつ → 検証(2軸・並列) → HTML レポート
```

途中で止まるのは **スコープ逸脱**(Step 6)と **検証で ⚠️/❌ が出たとき**(build-verify の Step 6)だけ。

## 5原則(build-kit 共通)

1. **スコープ宣言** — 触る範囲を先に宣言する。宣言外に手が伸びたら**止まって報告**。黙って広げない
2. **証拠なき完了宣言の禁止** — 「できた」と言うには証拠が要る。「通るはず」は証拠ではない
3. **段階ゲート** — **判断がユーザーのものである境界**では必ず止まる
   (設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。
   逆に「作業を続けていいですか」だけのためには止まらない — それは判断ではない
4. **気づきの報告義務** — 気づいたことは**必ず言う。ただし実行はしない**。
   言うことが無ければ「無し」と書く。**黙って見送るのは違反**
5. **出力の型** — 1行目は結論か次の行動。**段階の現在地(どの段階か / T2 of T5 のどこか)を毎回書く**。
   前置きと締めの挨拶を書かない。詳細は `${CLAUDE_PLUGIN_ROOT}/templates/output-style.md`

この段階は 1 と 4 が主戦場になる。**手が伸びるのを止めるのがこの skill の仕事。**

## Step 0: 入力を読む

1. `.build-kit/config.yaml` — `test_command` / `test_one_command` / `tdd_mode` / `protected_paths`
2. `plan.md` — タスク一覧、スコープ宣言、受入条件→テスト対応
3. **どこから始めるかを決める**(下記)

計画が無い場合、**実装を始めずに build-plan に戻す。**

### 開始位置の決定

タスクには `plan.md` で `T1` `T2` … と依存順に番号が振られている。
進捗はチェックボックス(`[ ] RED 書いた / …`)で判断する。

**未完タスクの先頭から、残り全部をやり切る。** 部分実行はしない。

タスクを指定されても受け付けない。受入条件は**計画全体に対して**定義されているので、
途中で止めると検証が成立せず、「未確認」だらけの判定表が出るだけになる。
一部だけ直したいなら、それは別の計画(=別の `/build-design`)にすべき対象。

前回の続きから入った場合は、**どこから再開するかを1行で伝える**:

> T1・T2 は完了済みです。T3 から残り3タスクを進めます。

## Step 1: タスクを1つ取る

**同時に複数のタスクを進めない。** 1タスクを RED→GREEN→REFACTOR で閉じてから次に行く。

タスク開始時に宣言する:

> T3「未入力を弾く」に入ります。触るのは `hooks/useForm.ts` と `__tests__/useForm.test.ts` です。

## Step 2: RED — 失敗するテストを書く

計画に書いた **RED** のとおりにテストを書く。実装コードはまだ書かない。

## Step 3: 失敗を目視する(★飛ばさない)

テストを走らせる。`test_one_command` があればそのタスクのテストだけを走らせる
(無ければ `test_command` を丸ごと)。

**出力を実際に見る。** そして計画に書いた「失敗の期待」と照合する:

| 照合結果 | やること |
|---|---|
| 期待どおりの理由で失敗 | GREEN へ進む |
| **違う理由で失敗**(import エラー、typo、設定不備) | テストを直す。**実装には進まない** |
| **なぜか成功してしまう** | そのテストは何も検証していない。**止まって報告する** |

3つ目が一番危ない。テストが通ってしまったら、それは
「すでに実装済み」か「テストが壊れている」のどちらか。**勝手に判断せず報告する。**

## Step 4: GREEN — 最小実装で通す

テストを通すための**最小の実装**を書く。計画の GREEN 方針に従う。

- 先回りして機能を足さない。テストが要求していないものは書かない
- **使い捨てのコードに抽象化を作らない**
- **頼まれていない「柔軟性」「設定可能性」を足さない**
- **起こり得ない状況のエラーハンドリングを書かない**
- 200行書いたが50行で済むなら、書き直す
- 「ついでに」他の箇所を直さない(→ Step 6)
- コーディング規約は PJ の CLAUDE.md に従う。build-kit は規約を持たない

自問する: **「シニアエンジニアがこれを見て『複雑すぎる』と言うか?」** 言うなら簡潔にする。

テストを走らせて緑を確認する。**緑になった出力を見るまで「通った」と言わない。**

## Step 4.5: 緑にならないとき — 先に根本原因を特定する

```
根本原因の調査なしに修正を試さない
```

テストが通らない、想定と違う落ち方をする、直したはずが直っていない —
このとき**当てずっぽうの修正を重ねない。** 症状を潰すだけの修正は失敗とみなす。

順に確認する:

1. **エラーメッセージを最後まで読む** — スタックトレース全部、行番号、エラーコード。
   飛ばさない。答えがそこに書いてあることが多い
2. **再現するか** — 毎回起きるか。手順は何か。再現しないなら、推測せずデータを集める
3. **直前に何を変えたか** — `git diff`、直近のコミット、設定の変更
4. **層をまたぐなら境界にログを置く** — 各コンポーネントの入口と出口で
   何が入って何が出たかを1回記録し、**どこで壊れているかを特定してから**その層を調べる

**急いでいるときほどこれを飛ばさない。** 当てずっぽうの往復のほうが結局遅い。

原因が分かったら、それが「今回の実装の問題」なのか
「テストの書き方の問題」なのか「計画の前提の間違い」なのかを言い、
3つ目なら**止まって報告する**(計画に戻る判断はユーザーのもの)。

## Step 5: REFACTOR

緑を保ったまま整理する。重複の除去、命名の改善、責務の分離。
リファクタ後に**もう一度テストを走らせて緑を確認する。**

整理するところが無ければ「無し」でよい。無理に触らない。

### 孤児の片付け(自分のゴミだけ)

**自分の変更が生んだ**未使用の import / 変数 / 関数は消す。

**元からあった dead code は消さない。** 気づいたら「気づき」として報告するだけ
(→ Step 8)。この線引きを守る。「ついでに掃除」は原則1の違反。

## Step 6: スコープの番人(★この skill の核)

### 判定基準

```
変更した全ての行が、ユーザーの要求まで直線で辿れるか
```

辿れない行があるなら、それは頼まれていない変更。消すか、下の手順で確認を取る。

### 宣言外のファイルに手が伸びたとき

実装中に、計画のスコープ宣言に**無いファイル**を触る必要が出たとき:

```
止まる → 報告する → 判断を仰ぐ
```

報告のしかた:

> T3 の実装中に、`store/formStore.ts` も変える必要が出ました。
> 理由: バリデーション結果を画面間で共有しないと受入条件2が満たせないためです。
> これは計画のスコープ外です。次のどれにしますか。
>
> 1. スコープに追加して続ける
> 2. 別タスクとして切り出し、今回は見送る
> 3. 設計に戻して考え直す

**黙って広げるのは違反。黙って諦めるのも違反。** 必ず選択肢として出す。

`protected_paths` に該当するファイルは、計画に明記されていても**改めて確認を取る。**

同様に、実装中に目に入った**関係ない問題**(古い TODO、明らかなバグ、重複コード)は:

- **その場では直さない**
- 「気づき」として記録し、タスク完了時に報告する

## Step 7: 変更理由を記録する

タスクを閉じるたびに、触ったファイルごとに**なぜ変えたかを1行**で記録する。
これが最終レポートの材料になる。

`<docs_dir>/<日付>-<slug>/changes.md` に追記する形でよい:

```markdown
## T3: 未入力を弾く
- `hooks/useForm.ts` (変更) — 保存前に必須項目を検査する validate() を追加
- `__tests__/useForm.test.ts` (新規) — 未入力・空白のみ・正常値の3ケース
```

あわせて `plan.md` のチェックボックスを更新する。

## Step 8: タスク完了の報告

1タスク終わるごとに簡潔に報告する:

> T3 完了。RED で「validate は関数ではない」を確認 → GREEN で通しました。
> テスト: 3 passed。触ったファイルは宣言どおり2つです。
> 気づき: `useForm.ts` の他の箇所に同じ検査が重複しています(今回は触っていません)。

**気づきが無ければ「気づき: 無し」と書く。** 省略しない。

次のタスクへ進む。全タスクが終わったら Step 9。

## Step 9: そのまま build-verify へ続ける

全タスク完了時:

> 全 N タスク完了しました。続けて検証に入ります。
> ここまでの気づき: <列挙、無ければ「無し」>

**ここで「実装が完了しました」とは言わない。** 検証がまだだから。
タスクが終わったことと、機能ができたことは別。

**そして、ここで承認を待たない。** ユーザーの追加コマンドなしに build-verify に入る。

> 検証は「突き進む」ことではなく「確認する」こと。
> ここで止まるほうが原則2(証拠なき完了宣言の禁止)に近い。

build-verify → build-report まで通しで実行し、**レポートを開いて終わる。**
途中で止まるのは、検証で ❌ か ⚠️ が出たときだけ(build-verify の Step 6)。
