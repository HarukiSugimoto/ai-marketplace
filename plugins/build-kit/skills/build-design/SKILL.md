# build-design — 何を作るかを決める

build-kit の入口。**ここでコードは書かない。**

**この skill は設計だけで終わらない。** 設計の承認が出たら、そのまま build-plan に続けて
`plan.md` まで作り、**実装の直前(計画の承認ゲート)で止まる。**

```
詰める → design.md → [■1 設計の承認] → plan.md → [■2 計画の承認] → 実装 → 検証 → レポート
```

**段階の切り替わりでユーザーの入力を待たない。** 止まるのは判断が要る4箇所だけ
(設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。

## 5原則(build-kit 共通)

1. **スコープ宣言** — 触る範囲を先に宣言する。宣言外に手が伸びたら**止まって報告**。黙って広げない
2. **証拠なき完了宣言の禁止** — 「できた」と言うには証拠が要る。「通るはず」は証拠ではない
3. **段階ゲート** — **判断がユーザーのものである境界**では必ず止まる
   (設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。
   逆に「作業を続けていいですか」だけのためには止まらない — それは判断ではない
4. **気づきの報告義務** — 気づいたことは**必ず言う。ただし実行はしない**。
   言うことが無ければ「無し」と書く。**黙って見送るのは違反**
5. **出力の型** — 1行目は結論か次の行動。**段階の現在地(どの段階か / T2 of T5 のどこか)を毎回書く**。
   前置きと締めの挨拶を書かない。詳細は `${CLAUDE_PLUGIN_ROOT}/templates/output-style.md`

この段階で特に効くのは 3 と 4。設計の承認が出るまで、いかなる実装アクションも取らない。

## Step 0: 設定の解決

カレントから上へ `.build-kit/config.yaml` を探す。

- **あれば** `docs_dir` / `test_command` / `tdd_mode` / `protected_paths` / レビュー設定を読み、
  後段の既定値にする
- **無ければ**、先に `/build-setup` を勧めて**ここで止まる**:

  > このPJにはまだ `.build-kit/config.yaml` がありません。
  > 先に `/build-setup` を走らせると、テストコマンド・成果物の置き場所・
  > このPJのレビュー手段を確定できます(1回だけ)。
  > このまま設計から始めることもできますが、検証段階で毎回聞くことになります。

  ユーザーが「このまま進めて」と言うなら続行する。その場合、検証に必要な情報は
  build-plan で聞くことになる。

**CLAUDE.md は複製しない。** 命名規約やディレクトリ構造は PJ の CLAUDE.md が既に効いている。
build-kit が扱うのは「段階の進め方」だけで、コーディング規約はそちらに任せる。

## Step 1: 何を解くかを詰める(★この段階の本体)

いきなり「どう作るか」に行かない。**まず何が困っていて、どうなれば解決かを言語化する。**

### 事実と決定を分ける(最重要)

```
事実を見つけるのは自分の仕事。決定を下すのはユーザーの仕事。
```

**環境を調べれば分かることを、ユーザーに聞かない。** 既存の型定義、今のディレクトリ構造、
使っているライブラリのバージョン、似た実装が既にあるか、テストがどう書かれているか —
これらは全部**自分で読みに行く。** 聞いた時点で違反。

聞いてよいのは**決定**だけ。「どちらを選ぶか」「どこまでやるか」「何を優先するか」。
調べれば分かる事実を質問に混ぜると、ユーザーの時間を奪ううえに、
答えを待つ間に自分で確認できたはずの前提を放置することになる。

### 決定木と frontier

未決事項を**決定木**として捉える。ある決定は、それが片付いて初めて意味を持つ
別の決定にぶら下がっている。

**frontier** = 前提がすでに片付いていて、**いま聞ける**決定の集合。
まだ答えを聞いていない決定に依存する質問は、frontier ではない。それは次のラウンド。

進め方:

1. 現状を調べる(関連ファイル・既存の設計ドキュメント・直近のコミット)
2. frontier を洗い出す
3. **frontier をまとめて1ラウンドで聞く**(AskUserQuestion が使えるなら最大4問。
   無いハーネスでは**番号を振って1メッセージにまとめる** — 1問ずつ小出しにしない)
4. 答えが木を作り変える。frontier を再計算して次のラウンド
5. **frontier が空になったら終わり**

各ラウンドで、質問には必ず**推奨する答えを添える**。「どうしますか」と丸投げしない。
自分ならどれを選ぶか、なぜかを示したうえで選ばせる。
選択肢の1つ目を推奨にして `(推奨)` と付ける。

同じラウンドに、互いに依存する質問を混ぜない。
「A を採るなら B はどうする?」は、A が決まってから聞く。

### 終了条件

**frontier が空 = 決定木の全ての枝を訪れ、黙って仮定したものが1つも無い状態。**

「だいたい分かったからもう作り始めよう」で切り上げない。
未決のまま進めた決定は、後で必ず手戻りになる。

### 詰めるべき軸

- 目的 — これが無いと何が困るのか
- 利用者 — 誰がいつ使うのか
- 成功の定義 — **どうなったら完成と言えるか**(ここが後の受入条件になる)
- 制約 — 期限・既存構造・使う技術で決まっているもの
- **やらないこと** — スコープの外側。ここを決めないと後で膨らむ

**規模の確認を先にする。** 依頼が複数の独立した機能を含むなら、その場で指摘して分割を提案する。
1つの設計メモに収まらないものを無理に1枚に押し込まない。

## Step 2: 案を2〜3出す

1案だけ出して「これでいいですか」と聞かない。**トレードオフのある選択肢を並べ、推奨を明示する。**

| 案 | 概要 | 利点 | 欠点 |
|---|---|---|---|

推奨案とその理由を1〜2行で述べ、ユーザーに選ばせる。

案が実質1つしかないとき(制約で決まりきっているとき)は、**「他に案が無い理由」を書く**。
無理に3案でっち上げない。

## Step 3: 設計を提示する

セクション単位で出し、**セクションごとに「ここまで合っていますか」と確認**する。
全部書いてから一括承認を求めない。

出すのは、この変更に**関係するものだけ**:

- データ(スキーマ・型・状態の形。変更なら before/after)
- 画面 / インターフェース(UI 構造、または関数・エンドポイントのシグネチャ)
- 処理の流れ(主要パス + 異常系)
- 既存コードへの影響(どの層に波及するか。**次段のスコープ宣言の材料**)

関係ないセクションは書かない。分量はその項目の複雑さに合わせる。単純なら2〜3行でよい。

## Step 4: 受入条件の素案を作る

**「これが満たされたら完成」を、判定できる粒度で列挙する。**

次の段階(build-plan)でこれを**テストの形まで落とす**ので、ここでは日本語でよい。
ただし判定不能なものは書かない:

| 書いてよい | 書いてはいけない |
|---|---|
| 未入力で保存すると「必須です」が出る | 使いやすくなっている |
| 一覧が更新日の降順で並ぶ | パフォーマンスが良い |
| 通信失敗時にリトライボタンが出る | ちゃんと動く |

## Step 5: 設計メモを書く

`<docs_dir>/<YYYY-MM-DD>-<slug>/design.md` に保存する
(`docs_dir` の既定は `docs/dev`。config.yaml があればそれに従う)。

雛形は `${CLAUDE_PLUGIN_ROOT}/templates/design.md`。**「気づき」欄を必ず埋める** —
頼まれていないが目に入った問題があれば書く。無ければ「無し」と書く。空欄で出さない。

config.yaml が無かった場合、ここで作成を提案する
(雛形: `${CLAUDE_PLUGIN_ROOT}/templates/config.yaml`)。

## Step 6: ゲート1(設計の承認)

設計メモのパスを示し、こう聞く:

> 設計を `<パス>` に書きました。読んで、直したいところがあれば言ってください。
> このまま進めていいなら、続けて実装計画まで作ります。

**ここで止まる。** ユーザーの承認が出るまで:

- コードを書かない
- ファイルを作らない(設計メモと config.yaml を除く)
- 計画に進まない

修正要求が来たら設計メモを直し、もう一度このゲートに戻る。

## Step 7: そのまま build-plan へ続ける

**承認が出たら、ユーザーの追加コマンドを待たずに build-plan に入る。**

「計画を作り始めていいですか」とは聞かない。**承認すべきは計画の中身であって、
計画を作る許可ではない。** 設計に GO が出た時点で、計画を作るのは決まっている。

> 承認ありがとうございます。続けて実装計画を作ります。

build-plan の Step 0 から通しで実行し、**計画の承認ゲート(build-plan の Step 5)で止まる。**
そこが実装に入る前の最後の関門で、承認が出たらそのまま実装 → 検証 → レポートまで進む。
