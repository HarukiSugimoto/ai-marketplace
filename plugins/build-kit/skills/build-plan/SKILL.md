# build-plan — どう作るかを決める

設計メモを **実行可能なタスク列**に変換する。**ここでもまだコードは書かない。**

**この skill も計画だけで終わらない。** 計画の承認が出たら、そのまま build-run に続けて
実装 → 検証 → レポートまで通す。

## 5原則(build-kit 共通)

1. **スコープ宣言** — 触る範囲を先に宣言する。宣言外に手が伸びたら**止まって報告**。黙って広げない
2. **証拠なき完了宣言の禁止** — 「できた」と言うには証拠が要る。「通るはず」は証拠ではない
3. **段階ゲート** — **判断がユーザーのものである境界**では必ず止まる
   (設計の承認 / 計画の承認 / スコープ逸脱 / 未確認の扱い)。
   逆に「作業を続けていいですか」だけのためには止まらない — それは判断ではない
4. **気づきの報告義務** — 気づいたことは**必ず言う。ただし実行はしない**。
   言うことが無ければ「無し」と書く。**黙って見送るのは違反**
5. **出力の型** — 1行目は結論か次の行動。**段階の現在地(どの段階か / `02 of 05` のどこか)を毎回書く**。
   前置きと締めの挨拶を書かない。詳細は `${CLAUDE_PLUGIN_ROOT}/templates/output-style.md`

この段階の産物がそのまま 1 と 2 の土台になる。
**スコープ宣言と受入条件を、実装が始まる前にここで固定する** —
後から基準を足したり緩めたりできないようにするのが目的。

## Step 0: 入力を読む

1. `.build-kit/config.yaml`(カレントから上へ探す)— `test_command` / `test_one_command` /
   `tdd_mode` / `test_layout` / `protected_paths` / `docs_dir`
2. 対象の `design.md` — 直近の `<docs_dir>/<日付>-<slug>/design.md`、
   または @ で指定されたもの
3. 実際のコード — 設計メモの「既存コードへの影響」に挙がった箇所を**実際に開いて確認する**。
   設計時の想定と現物がズレていたら、ここで報告する(黙って計画を書き換えない)

**事実を見つけるのは自分の仕事。** 既存のテストの書き方、モックの慣習、
似た機能がどう実装されているか、テストランナーの設定 — 全部自分で読みに行く。
ユーザーに聞いてよいのは**決定**(どちらを選ぶか)だけ。調べれば分かることを質問しない。

設計メモが無い場合は、**build-plan を続けずに build-design に戻す。**
「設計なしで計画だけ作る」はしない。

## Step 1: 受入条件をテストに落とす(★この段階の核)

前提は **TDD**。設計の受入条件を、**どのテストが判定するか**まで落とす。

| # | 受入条件 | 判定するテスト | テストが無い場合の証拠 |
|---|---|---|---|
| 1 | 未入力で保存すると「必須です」が出る | `__tests__/form.test.ts` の `未入力なら必須エラーを返す` | — |
| 2 | 一覧が更新日の降順で並ぶ | `__tests__/list.test.ts` の `更新日降順で返る` | — |
| 3 | ローディング中はスピナーが出る | — | 実際に画面を出して確認した記録 |

**テストで判定できないものは、代わりに何を証拠にするかをここで決めておく。**
検証段階で基準を後出しさせないため。決められないなら、その受入条件は
判定不能なので設計に戻して書き直す。

`tdd_mode: strict`(既定)ならテスト免除は原則なし。
`pragmatic` の場合のみ、免除タスクと**理由**を計画に明記する。
理由が「面倒」「時間がない」なら免除を認めない。書けないなら免除しない。

## Step 2: スコープを宣言する

**触る範囲を宣言する。単一ファイルでも、glob でもよい。**

| 範囲 | 新規/変更 | 何をするか |
|---|---|---|
| `src/auth/**` | 変更 | パスワードリセットの導線を足す |
| `src/mail/templates/reset.tsx` | 新規 | リセットメールの本文 |

**実装前にファイルを全部言い当てるのは無理。** 面(ディレクトリ)で宣言してよい。
点で書けるものは点で書く。

### 粒度の歯止め

範囲を広く取りすぎると原則1が骨抜きになる。上限は:

```
1つの範囲 = 1つのモジュール。その中で何が起きるかを1行で説明できること
```

- ⭕ `src/auth/**`、`src/mail/templates/*.tsx`
- ❌ `src/**`、`**/*.ts`、`.`(**何も宣言していないのと同じ**)

**glob を使うなら「触らないと明言するもの」が効いてくる。** 面で宣言した中に
触ってほしくないものがあるなら、ここで**除外として名指しする:**

```
- `src/auth/session.ts` — 触らない。今回は導線だけでセッション管理は変えない
- `db/schema.ts` — 触らない。クエリ層のみ
```

除外は**範囲宣言より強い**。glob に含まれていても、ここに名前があれば build-run は止まる。

### テストファイルは宣言しなくてよい

各タスクの **RED に書いたテストファイルは、自動的にスコープに含まれる。**
TDD 前提なので必ず書くことが分かっており、宣言を求めるのは儀式。

**RED に書いていないテストファイルを触るのは宣言外。** これは止まる。

### protected_paths

config の `protected_paths` に該当するファイルを触る必要がある場合、
**この時点でユーザーに確認を取る。** 計画に黙って含めない。

`protected_paths` は**範囲宣言でも `auto_scope` でも免除されない。**
glob で面を宣言した中に含まれていても、build-run は毎回確認を取る。

## Step 3: タスクに分解する

### 形の基準 — 縦に切る

```
1タスクは細くてよい。ただし schema / API / UI / test の
全レイヤーを貫く、完全な1本の経路であること
```

**1レイヤーだけの水平タスクを作らない。** 「スキーマだけ変える」「API だけ作る」は
それ単独では何もできるようにならないので、タスクではない。

判定は1つ:

> **「このタスクを閉じると、ユーザーから見て何ができるようになるか」が1行で書けるか。**

書けないなら水平に切れている。切り直す。

### 大きさの基準

```
1タスク = 自分のテストサイクルを1周持ち、
          レビュアーが単独で却下しうる最小の単位
```

「ファイルを作る」はタスクではない。「未入力を弾く」がタスク。

- **セットアップ・設定・足場・ドキュメントは、それを必要とする成果物のタスクに畳み込む。**
  独立したタスクにしない
- **分けるのは、レビュアーが片方を却下しつつ隣を承認できる場合だけ**
- 各タスクは、それ単独でテスト可能な成果物で終わる

タスクが5〜6個を超えるなら、設計が大きすぎる。分割をユーザーに提案する
(**広域変更はこの上限の対象外** — 後述)。

### 先に楽にする — prefactoring

```
変更しやすくしてから、変更する
```

分解の前に、**既存コードを整えるだけで後続が明らかに楽になる箇所**を探す。
あれば **01 に置く**(振る舞いを変えないタスクなので、受入条件には紐づかない)。

- ここでの「整える」は**振る舞いを変えない移動・改名・抽出**だけ。
  ついでの機能追加やバグ修正を混ぜない
- 楽になる根拠を1行書く。書けないなら prefactoring ではなく、ただの掃除なのでやらない

### 例外 — 広域変更は縦に切れない

リネーム、共有型の付け替えのように、**1箇所直すと全呼び出し元が同時に壊れる**変更は、
どう縦に切っても各タスクで緑にならない。無理に縦割りにせず、**expand → contract** で並べる:

```
1. expand    新形式を旧の隣に追加する。旧が残っているので何も壊れない
2. migrate   呼び出し元を移行する。バッチは影響範囲で切る
             (パッケージ単位 / ディレクトリ単位)。各バッチは expand にだけ依存し、
             旧形式がまだあるので単独で緑になる
3. contract  呼び出し元がゼロになったら旧形式を削除する。
             全 migrate バッチに依存する
```

migrate バッチ同士は**互いに独立**なので、そのまま並列に着手できる。

バッチ単体でも緑にできない場合だけ、**最後に統合タスクを1つ置き、緑はそこでだけ約束する**
(この場合は計画にその旨を明記する。緑にならないタスクが並ぶのは通常は違反なので、
理由を書かないと build-run が止まる)。

### 依存を宣言する

**各タスクに `Blocked by` を書く。** 先に終わっている必要があるタスクの番号だけを書き、
理由を括弧で1行添える。

```
Blocked by: 01(sortKey 型が要る)
Blocked by: なし — すぐ着手可
```

**ここが build-run の順序を決める。** build-run は「上から順」ではなく
「ブロッカーが全部済んだタスク」から取るので、**書き漏らすと、まだ存在しない関数を
使う実装が始まる。** 番号順に並んでいるからといって暗黙に守られたりはしない。

書くのは**本当に先行が要るものだけ**。「なんとなく先にやりたい」は依存ではない。
過剰に依存を張ると、着手できるタスクが1本道になって迂回できなくなる。

### 各タスクに書くこと

- **RED**: どのテストファイルに、どういうテスト名で、何を検証するか
- **失敗の期待**: **どう失敗すれば正しいか。**「未定義エラー」なのか「値が違う」なのか。
  ここを書いておかないと、実装段階で「間違った理由で失敗しているテスト」を
  緑にして満足してしまう
- **GREEN**: 最小実装の方針
- **触るファイル**: スコープ宣言のどれか
- **インターフェース**:
  - `使うもの` — 先行タスクから受け取る関数・型の**正確なシグネチャ**
  - `出すもの` — 後続タスクが依存する関数名・引数・戻り値の型

**インターフェース欄は必須。** build-run は1タスクずつ進めるので、
実装時に見えるのは自分のタスクだけになる。隣のタスクが何という名前で
何を返すかを知る手段が、ここしかない。

**`使うもの` と `Blocked by` は一致する。** 先行タスクから何かを受け取るなら、
そのタスクは必ずブロッカー。片方だけ書いてあるのは書き漏らし。

### 全体制約

PJ 全体にかかる要件(ライブラリのバージョン下限、命名規則、対応プラットフォーム、
文言のルール)は、**設計メモから逐語でコピーして計画の冒頭に1行ずつ置く。**
全タスクの要件に暗黙に含まれるものとして扱う。

## Step 4: 計画を書く — 1タスク1ファイル

`<docs_dir>/<YYYY-MM-DD>-<slug>/` に保存する(design.md と同じディレクトリ)。

```
<docs_dir>/<YYYY-MM-DD>-<slug>/
├── design.md
├── plan.md            計画全体にかかるもの
└── tasks/
    ├── 01-<slug>.md   タスク1つ
    ├── 02-<slug>.md
    └── 03-<slug>.md
```

| ファイル | 持つもの | 雛形 |
|---|---|---|
| `plan.md` | 全体制約 / スコープ宣言 / 受入条件→テスト対応 / 依存の見取り図 / テスト免除 / リスク / 気づき | `${CLAUDE_PLUGIN_ROOT}/templates/plan.md` |
| `tasks/<NN>-<slug>.md` | Blocked by / 何ができるようになるか / RED / 失敗の期待 / GREEN / 触るファイル / インターフェース / 進捗 / 気づき | `${CLAUDE_PLUGIN_ROOT}/templates/task.md` |

番号は **`01` から、依存の浅い順**に振る(ブロッカーが先の番号になるように)。
ただし**番号は順序の保証ではない** — 実行順を決めるのは `Blocked by` だけ。

### 依存の正はタスクファイル側

`plan.md` にも依存の表と「着手できる順」を書くが、**これは計画時点の見取り図**。
`tasks/*.md` の `Blocked by` とズレたら、**タスクファイルが勝つ。**

分割の目的は、**タスクファイル1枚を単独で渡しても実装できる**ことにある。
そのファイルが依存について嘘をつくと分割の意味が消えるので、正はそちら側に置く。

**「気づき」欄を必ず埋める。** 計画を立てる過程で目に入った、
今回のスコープ外の問題を書く。実行はしない、報告だけ。無ければ「無し」と書く。

## Step 5: ゲート2(計画の承認)— 実装前の最後の関門

計画のパスを示し、こう聞く:

> 計画を `<パス>` に書きました。タスクは N 個、触るファイルは M 個です。
> 最初に着手できるのは <番号列> の <K> 個です。
>
> 1. スコープと受入条件に、抜けや余計なものはありますか
> 2. **依存は合っていますか** — <各タスクの Blocked by を1行ずつ列挙>
>
> よければこのまま実装に入ります。

**依存は独立した項目として聞く。** スコープと受入条件に混ぜない。
build-run は上から順ではなく `Blocked by` を見て進むので、
ここの誤りは「まだ無い関数を使う実装」になって現れる。**目視で潰せるのはここだけ。**

**ここで止まる。** 承認が出るまで実装に入らない。
ここは build-kit で最も重要なゲートで、スコープと受入条件がここで固定されると、
以降は実装が終わるまで人が介在しない(スコープ逸脱を除く)。

修正要求が来たら計画を直し、もう一度このゲートに戻る。

## Step 6: そのまま build-run へ続ける

**承認が出たら、ユーザーの追加コマンドを待たずに build-run に入る。**

コマンドを打ち直させない。**承認すべきは計画の中身であって、実装を始める許可ではない。**
計画に GO が出た時点で、実装するのは決まっている。

> 承認ありがとうございます。01 から実装に入ります(01 と 03 が着手可、まず 01)。

build-run → build-verify → build-report まで通しで実行し、**レポートを開いて終わる。**
途中で止まるのはスコープ逸脱と、検証で ⚠️/❌ が出たときだけ。
