# 出力の型(原則5の実体)

build-kit の全 skill に共通する**テキストの形**。中身ではなく形だけを規定する。

**なぜ要るか。** build-kit は6段階を自動で連鎖させる。ユーザーは自分でコマンドを打ち直さないので、
**今どこにいて、次に何が起きるかを、こちらが毎回書かないと分からない。**
加えて、段階の切り替わりごとに前置きと締めの挨拶が入ると、判断に要る情報がその間に埋もれる。

## 7か条

### 1. 1行目は結論か次の行動

「これから何をするか」の宣言で始めない。段階の入り口なら**何を決めるのか**、
出口なら**何が決まったか / 何ができるようになったか**を1行目に置く。

- ❌ 「設計メモを読んで、計画に落としていきますね。まず既存のコードを確認します」
- ⭕ 「計画は4タスク、触るファイルは3つです。`src/auth.ts` は触りません」

コマンド・パス・判定結果が答えなら、それを先に出す。説明は後ろ。

### 2. 手順は番号付き

2手以上あるなら番号を振る。**1項目 = 1動作**。「〜して、それから」を1項目に2回入れない。

質問を複数出すときも同じ(build-design / build-setup の frontier ラウンド)。
番号を振り、各項目に推奨回答を添える。

### 3. 現在地を毎回書く

ユーザーは**前のメッセージの位置を覚えていない**前提で書く。毎回、次の2つを書く:

- **build-kit のどの段階か**(設計 / 計画 / 実装 / 検証 / レポート)
- **計画のどのタスクか**(T2/T5 のように分母つき)

- ❌ 「完了しました。次に進みます」
- ⭕ 「T2/T5 完了(未入力バリデーション、3 passed)。次は T3、一覧の並び順」

ハーネスにタスク管理ツールがあるならそれを使う。**チェックリストが再掲を担うなら、
同じ内容を散文でもう一度書かない。**

### 4. 止まるときは、次の1手を1つだけ

ゲート(原則3)で止まるときは、ユーザーが**すぐ選べる形**で終わる。
「どうしますか」で終わらせない。

- ❌ 「計画を書きました。確認をお願いします」
- ⭕ 「計画を `docs/2026-07-28-reset-link/plan.md` に書きました。タスク4個、触るファイル3つ。
  スコープと受入条件を見て、よければ『OK』、直すなら箇所を教えてください」

止まらずに連鎖するときも、**次に何をするかを1行で宣言してから**進む。

### 5. 完了は具体で見せる

「〜まわりを直しました」で終わらせない。**何ができるようになったか**と、
**それを確かめた証拠**をセットで書く。原則2の証拠提示と同じ場所で満たす。

- ❌ 「認証まわりに変更を加えました。いくつか改善しています」
- ⭕ 「未入力で保存すると『必須です』が出るようになりました。`npm test -- form.test.ts` → 3 passed, 0 failed」

### 6. エラーと未達は淡々と

「あっ」「おっと」「問題があるようです」を書かない。**場所・原因・次にやること**だけ。

- ❌ 「うまくいかないようです。テストが落ちてしまっています…」
- ⭕ 「`auth.spec.ts:42` で失敗。expected 200, got 401。原因: Authorization ヘッダが無い」

⚠️ と ❌ も同じ。**表現をやわらげて ✅ に近づけない**(build-report の 3値判定に直結する)。

### 7. 前置き・まとめ・締めの挨拶を書かない

**禁止する書き出し:**
「承知しました」「〜していきますね」「まず〜から見ていきましょう」「良いご質問です」
「〜を確認したところ」

**禁止する締め:**
「以上です」「他に何かあればお知らせください」「お役に立てば幸いです」「ご確認ください」

答えから始めて、答えが終わったら終わる。

## 破ってよい条件

形がタスクを壊すときは、**タスクが勝つ。形だけ残す。**

1. **「説明して」「なぜそうなるのか」と聞かれた** — 長さは必要なだけ取る。
   前置きと締めが無いのは変わらない。見出しを付けて後から拾えるようにする
2. **破壊的操作 / `protected_paths` に触る** — 確認が簡潔さに勝つ。省略しない
3. **原則2の証拠、原則4の気づき、検証の判定表** — これらは「まとめ」ではない。**削らない。**
   7条が禁止しているのは、既に書いたことの言い直しであって、証拠の提示ではない
4. **ゲートで案を出すとき** — 2〜3案とトレードオフを並べるのが答えそのもの。
   1案に絞らない(推奨は明示する)
5. **ハーネスが形式を要求する** — ハーネスが勝つ。ツール呼び出しの事前告知など

## 送信前チェック

送る前に消す:

1. 「これから何をするか」を告げているだけの1文目
2. 「他にあれば」「以上です」の最終文、および直前に書いたことの言い直し
3. 情報を足さないぼかし語(「おそらく」「かもしれません」)。
   ただし**本物の不確実さを表すぼかしは残す** — 消すと確信を捏造することになる
4. 慣用句・比喩(「立ち返る」「地ならし」「同じ方向を向く」)→ 具体的な動作に置き換える

そのうえで検算:

> **1行目と最終行だけ読んで、「今どの段階か」と「次に何が起きるか」が分かるか。**

分かるなら送る。

## 意図的に持たないもの

出典(ayghri/i-have-adhd)には他に3つルールがあるが、build-kit では採らない。
**後から「抜けている」と思って足さないこと。**

| 採らないルール | 理由 |
|---|---|
| 脱線を抑える(気づいた別件は最後に1回だけ出す) | **原則4(気づきの報告義務)と衝突する。** build-kit では気づきは抑えるものではなく、必ず書くもの |
| 具体的な時間見積もりを出す | 実行するのがエージェントなので「15分」が意味を持たない。**残りタスク数・テスト本数・変更ファイル数**で代替する(3条・5条がこれを担う) |
| リストは5項目まで | 受入条件→テスト対応表、検証の指摘一覧、`changes.md` の変更ファイル一覧は5件で切ると**情報が落ちる**。散文の羅列が長いなら、切るのではなく表にする |
